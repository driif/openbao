# `kmip` listener

The KMIP listener serves the OASIS Key Management Interoperability Protocol
(KMIP 1.x) on a TCP address/port. KMIP clients authenticate with TLS client
certificates through a [cert auth method][cert-auth] mount, and their
operations act on keys in a [transit secrets engine][transit] mount.

```hcl
listener "kmip" {
  address            = "127.0.0.1:5696"
  tls_cert_file      = "/etc/openbao/kmip.crt"
  tls_key_file       = "/etc/openbao/kmip.key"
  tls_client_ca_file = "/etc/openbao/kmip-clients-ca.pem"
  auth_mount         = "auth/cert"
}
```

The listener does not serve the HTTP API. Each KMIP operation runs as one or
more ordinary OpenBao requests against the transit mount, made with the
client's token, certificate, and address. ACL policies, namespaces, audit
devices, resource quotas, and request forwarding from standby nodes therefore
apply to KMIP clients. A standby without an audit broker refuses operations
except Query and DiscoverVersions. Connect other clients to the active node.

KMIP listeners are not started in [recovery mode][recovery-mode]. When OpenBao
shuts down, it closes KMIP connections first so that their tokens are revoked.

:::info

This listener makes OpenBao a KMIP server. It is unrelated to the
[KMIP seal][kmip-seal], where OpenBao is a client of an external KMIP server.

:::

## `kmip` listener parameters

- `address` `(string: "127.0.0.1:5696")` – Specifies the address to bind to
  for KMIP connections. Port 5696 is the registered KMIP port. Like the `tcp`
  listener's `address`, this can be a
  [go-sockaddr template](https://pkg.go.dev/github.com/hashicorp/go-sockaddr/template).

- `auth_mount` `(string: <required>)` – The cert auth mount that clients log
  in through, including its namespace: `auth/cert` in the root namespace, or
  `ns1/auth/cert` for the mount `auth/cert` in the namespace `ns1`. Everything
  before the first `auth` segment is taken as the namespace, so the namespace
  path cannot contain a segment named `auth`. The transit mounts this listener
  uses are in the same namespace.

- `default_transit_mount` `(string: "")` – The transit mount, in the auth
  mount's namespace, used by clients whose cert role sets no
  `kmip_transit_mount`. If neither is set, the client's operations fail.

- `tls_cert_file` `(string: <required>, reloads-on-SIGHUP)` – The PEM-encoded
  server certificate. Behaves as on the [`tcp` listener][tcp-params].

- `tls_key_file` `(string: <required>, reloads-on-SIGHUP)` – The PEM-encoded
  private key for the certificate. Behaves as on the [`tcp` listener][tcp-params].

- `tls_client_ca_file` `(string: <required>)` – PEM-encoded CA file used to
  verify client certificates during the TLS handshake. The listener always
  requires and verifies a client certificate, whatever
  `tls_require_and_verify_client_cert` is set to. Cert auth checks the
  certificate again against its roles when the client logs in.

The following [`tcp` listener parameters][tcp-params] also apply, with the same
meaning:

- `tls_auto_reload` and `tls_auto_reload_interval`
- `tls_min_version`, `tls_max_version`, `tls_cipher_suites`, and
  `tls_key_exchange_preferences`
- `proxy_protocol_behavior` and `proxy_protocol_authorized_addrs`
- `max_request_duration`, which bounds each OpenBao request a KMIP operation
  makes

A `kmip` listener rejects `tls_disable`, `tls_disable_client_certs`,
`cluster_address`, and every `tls_acme_*` parameter. Parameters that only
concern HTTP, such as the `http_*` timeouts, `x_forwarded_for_*`,
`custom_response_headers`, and the `telemetry` and `profiling` stanzas, have no
use on a `kmip` listener; leave them unset. `auth_mount` and
`default_transit_mount` are rejected on other listener types.

## Authentication

A KMIP client authenticates with its TLS client certificate:

1. The TLS handshake verifies the certificate against `tls_client_ca_file`.

1. On the connection's first operation that needs OpenBao, the listener logs in
   through `<auth_mount>/login` without a role name, so cert auth uses the
   first role whose constraints match the certificate. Constrain KMIP roles,
   for example with `allowed_common_names`, so that each client certificate
   matches exactly one role.

1. The role's `kmip_transit_mount`, or else the listener's
   `default_transit_mount`, names the transit mount the client works on. The
   role's `kmip_key_prefix` names the keys the client creates or registers
   without a name, and its `kmip_rekey_retain` bounds how many generations
   ReKey keeps readable. See the [cert role parameters][cert-role].

The token never leaves OpenBao and lives as long as the connection. When it is
a few seconds from expiring, the next operation logs in again. When the
connection closes, the listener revokes a service token; a batch token simply
expires. Cert auth checks the certificate against the role, including CRLs and
OCSP where configured, at every login, so the role's `token_ttl` bounds how
long an open connection keeps working after its certificate is revoked or its
role changes.

OpenBao answers an expired token and a policy denial with the same error. When
a request is denied, the listener therefore logs in again and retries the
request once, so a denied operation is audited twice, with a new login in
between.

The listener answers Query and DiscoverVersions itself, without logging in.

## Keys and operations

A KMIP managed object is a transit key plus the `kmip/` entries of the key's
[metadata record][transit-key-metadata]. The transit key holds the material,
type, versions, and soft-delete; the record holds what transit cannot: stored
attributes, Link attributes, the object's Name across ReKey, and the
compromise and destroy marks.

A key's KMIP Unique Identifier is its transit key name. Create and Register use
the request's Name attribute as the key name. Without one, the key is named
`<kmip_key_prefix><uuid>`. Key names may only contain letters, digits, `_`,
`-`, and `.`. A Name that ends in `.` and digits, such as `app.2`, is refused:
those names are reserved for the replacements ReKey creates.

The listener supports Create, Register, Get, GetAttributes, GetAttributeList,
AddAttribute, ModifyAttribute, DeleteAttribute, ReKey, Locate, Activate,
Revoke, Destroy, Encrypt, Decrypt, Sign, SignatureVerify, Query, and
DiscoverVersions, with these key types:

| KMIP algorithm                | Length                         | Transit key type                         |
| :---------------------------- | :----------------------------- | :--------------------------------------- |
| AES                           | 128, 256                       | `aes128-gcm96`, `aes256-gcm96`           |
| ChaCha20, ChaCha20Poly1305    | 256                            | `chacha20-poly1305`                      |
| HMAC-SHA1 through HMAC-SHA512 | 256 to 4096, a multiple of 8   | `hmac`                                   |
| RSA                           | 2048, 3072, 4096               | `rsa-2048`, `rsa-3072`, `rsa-4096`       |
| ECDSA, EC                     | 256, 384, 521                  | `ecdsa-p256`, `ecdsa-p384`, `ecdsa-p521` |

- Register takes a SymmetricKey in Raw format or a PrivateKey in PKCS#8 DER
  format. The listener wraps the material with the mount's wrapping key and
  imports it.
- Get returns the material of the key's latest version: a Raw SymmetricKey for
  AES, ChaCha20, and HMAC keys, and a PKCS#8 PrivateKey for RSA and ECDSA keys.
- Activate, Revoke, and Destroy follow the KMIP lifecycle; see
  [Lifecycle](#lifecycle). Destroy never deletes the transit key.
- Encrypt, Decrypt, Sign, and SignatureVerify are single-part only and accept
  no Cryptographic Parameters, IV, or additional authenticated data. Encrypt
  returns transit's ciphertext string (`vault:v1:...`), which Decrypt takes
  back. Sign signs the SHA-256 digest of the data with the key's default
  transit signature algorithm and returns transit's signature string, which
  SignatureVerify takes back.
- Locate by exact Name or Unique Identifier reads the key and does not list.
  Any other filter lists the mount and reads every key, one read per key, plus
  the comparison of each filter attribute with the key's attributes. There is
  no attribute index, so the cost grows with the number of keys in the mount.

### Attributes

Attributes fall in four classes:

- **Derived** from the transit key and the record: Unique Identifier, Object
  Type, Cryptographic Algorithm, Cryptographic Length, State, and Initial Date.
- **Server-set** by Revoke and Destroy only: Compromise Date, Compromise
  Occurrence Date, Destroy Date, and Revocation Reason.
- **Honoured**: Name. An object's Name is the Unique Identifier of its first
  generation and moves to the replacement on ReKey. AddAttribute with the
  object's current Name succeeds and changes nothing; any other Name fails with
  Invalid Field, because renaming is not supported. ModifyAttribute and
  DeleteAttribute of Name fail with Invalid Field.
- **Stored**: every other attribute, standard or custom (`x-` and `y-`). The
  listener keeps each instance verbatim, returns it from GetAttributes and
  GetAttributeList, and matches it in Locate. A stored Cryptographic Usage Mask
  does not restrict Encrypt, Decrypt, Sign, or SignatureVerify. A stored
  Activation Date or Deactivation Date changes the reported State, as
  [Lifecycle](#lifecycle) describes, and nothing else. Activation Date is the
  key's creation time unless the client stored one.

AddAttribute, ModifyAttribute, and DeleteAttribute refuse derived and
server-set attributes with Permission Denied, and so does a Create, Register,
or ReKey template.

ModifyAttribute replaces one instance and DeleteAttribute removes one. Both
select it by Attribute Index, 0 when the request has none, numbered as
GetAttributes numbers them, and both return the instance with its index. The
Links ReKey wrote come first among the Link instances and cannot be changed.
ModifyAttribute of the Activation Date that no client stored stores the new
value; DeleteAttribute of it finds nothing. An index without an instance fails
with Item Not Found, since KMIP 1.x has no Attribute Not Found. Both refuse a
ReKey replacement that is still being created, as AddAttribute does.

Create and Register store the stored attributes of their template, by the
rules a ReKey template follows. A template with none, such as only
Cryptographic Algorithm, Cryptographic Length, and Name, sends no metadata
request. If that write fails, transit has already made the key, and the
operation fails with General Failure, naming the key. Transit answers a create
of an existing key with that key, so the listener soft-deletes the key, best
effort, only when no other client can hold it: after a Register, since
transit's import refuses an existing key, and after a Create without a Name,
whose generated name is a fresh UUID. A Create with a Name leaves the key
Active without its attributes, because another client can create the same
Name between the listener's read and its create, and both then hold the one
key. If the soft-delete fails, the key also stays Active, and the error says
so. Create with stored attributes reads the key first and refuses one that
exists, including a soft-deleted one, and a template write refuses a record
that already holds KMIP entries. A retry with the same Name therefore fails
until an operator restores, purges, or keeps the key.

Single-instance attributes, such as Cryptographic Usage Mask and the dates,
take one value: a second AddAttribute with a different value fails. The record
is limited to 64 KiB serialized, 1024 keys, 512 bytes per non-empty key,
and 8 KiB per value. Each `kmip/<entry>` value is a JSON array, so the 8 KiB
limit applies to the whole attribute entry, including all its instances.
A write over a limit fails with Invalid Field. The adapter reads the
record and replaces it with POST and `cas`, preserving unrelated entries.
It retries a CAS mismatch up to eight attempts, then returns General Failure
with a request to retry. Every check of an operation that writes the record
runs again on the record of each attempt. It never sends PATCH.

### Lifecycle

The listener derives an object's State, in this order:

1. **Destroyed**, or **Destroyed Compromised**: the record holds the destroy
   mark, and for Destroyed Compromised the compromise mark too.
2. **Compromised**: the record holds the compromise mark.
3. **Deactivated**: the key is soft-deleted, ReKey replaced it, or its
   Deactivation Date is at or before now.
4. **Pre-Active**: its Activation Date is after now.
5. **Active**: otherwise.

The marks are the `kmip/compromised` and `kmip/destroyed` entries of the
record. They are not attributes, and only Revoke and Destroy set them. The
dates change only the reported State: Encrypt, Decrypt, Sign, and
SignatureVerify read neither, and a key past its Deactivation Date still
works until it is soft-deleted. A refusal for the wrong State fails with
Permission Denied and a message that names the State, since KMIP 1.x has no
Wrong Key Lifecycle State reason.

- **Create and Register** make an Active object, unless the template holds an
  Activation Date in the future: the object is then Pre-Active until that date
  or until Activate.
- **Activate** of a Pre-Active object stores now as its Activation Date, which
  makes it Active. Activate of an Active object succeeds and writes nothing.
  Any other State is refused. A stored Activation Date or Deactivation Date
  that does not decode fails Activate with General Failure.
- **Revoke** with reason Key Compromise or CA Compromise sets the compromise
  mark, the Compromise Date (now), and the Compromise Occurrence Date: the
  request's, or else the Initial Date. A second compromise Revoke keeps the
  first dates. Any other reason sets the Deactivation Date to now, unless one
  at or before now is stored. Both store the Revocation Reason, then
  soft-delete the key, so transit refuses it for every cryptographic
  operation. Revoke refuses a Destroyed object; a Revoke with a reason other
  than a compromise also refuses a Pre-Active or Compromised object, as KMIP
  1.4 has no such transition. Revoke writes the record first: if the
  soft-delete then fails, the object already reports Compromised or
  Deactivated, and a retry soft-deletes the key and keeps the first dates.
- **Destroy** is soft. It refuses an Active object and succeeds without a
  write on a Destroyed one. On a Pre-Active, Deactivated, or Compromised object
  it soft-deletes the key unless it is soft-deleted already, then sets the
  destroy mark and the Destroy Date. It never deletes the key, so
  `deletion_allowed` has no effect on it. The soft-delete goes first, so Get
  never returns material of an object that reports Destroyed; an interrupted
  Destroy leaves the object Deactivated, and a retry finishes it. Get of a
  Destroyed object fails as for any soft-deleted key; GetAttributes still
  reports its State and dates.
- **ReKey** refuses a Compromised or Destroyed object. A replacement copies the
  stored dates, so a copied Deactivation Date in the past makes it report
  Deactivated.

Purging a destroyed key is an operator action outside KMIP: set
`deletion_allowed` with [`<mount>/keys/<name>/config`][transit-key-config],
then delete the key through transit. To undo a Destroy, restore the key with
transit's `soft-delete-restore`, then remove `kmip/destroyed` and
`kmip/attr/Destroy Date` from its metadata.

### ReKey

ReKey replaces a symmetric key with a new transit key, the next generation of
its Name. The first generation of a Name is its anchor, with the Unique
Identifier `<name>`; later generations are `<name>.2`, `<name>.3`, and so on.
The anchor's record names the current generation, so Locate by exact Name
reads at most two keys and their metadata when no ReKey moves the Name during
the lookup. If a concurrent ReKey moves it, Locate resolves the anchor again.

- The replacement gets the Name, the stored attributes, including Activation
  Date and Deactivation Date, and a Link of type Replaced Object to the
  predecessor. Template attributes in the request replace copied ones.
- The predecessor gets a Link of type Replacement Object, loses its Name, and
  reports State Deactivated. It is not soft-deleted, so Get still returns its
  material until retention removes it.
- ReKey sets the ID Placeholder to the replacement.
- ReKey refuses an Offset, a Compromised or Destroyed object, a key it already
  replaced, a soft-deleted key, and a template that changes the Name,
  algorithm, length, or object type, or that carries any other derived or
  server-set attribute, even one equal to the key's own.

The cert role's `kmip_rekey_retain` defaults to `0`, which keeps every
generation and sends no retention soft-delete. A positive value opts into the
sweep and sets how many generations stay readable, the current one included:
`2` keeps one predecessor and `1` keeps none. After the replacement holds the
Name, an enabled sweep soft-deletes older generations, oldest first. The anchor keeps its metadata record when its
material goes, so the Name still resolves. This sweep is best effort: when a
soft-delete fails, typically because the policy grants no `delete` on
`<mount>/keys/<name>/soft-delete`, ReKey still succeeds, the server logs a
warning that names the path and the capability, and the next ReKey of the Name
tries again.

ReKey commits when it claims the Name for the replacement in the anchor's
record, expecting the predecessor. Two concurrent ReKeys of one Name therefore
cannot both win, and the Name never moves back to an older generation. Every
other step is safe to repeat, so a client that retries an interrupted ReKey
completes it:

- Before it creates the replacement, ReKey records it as `pending_successor`
  in the predecessor's record, and clears the marker once the replacement's
  record is written. A retry that finds the replacement without a record
  adopts it only while the marker names it.
- The replacement's record is written once. A retry or a concurrent ReKey
  that finds it keeps it, so attributes added to the replacement since stay.
- A retry that finds the Name already moved past the replacement links the
  predecessor to the replacement and leaves the Name where it is.
- A concurrent ReKey of the same key that finds the replacement before its
  record is written reads both keys again, then adopts or resumes it.
- Any other existing key with the replacement's name fails the ReKey, and the
  error names that key. Retry the ReKey; if the error repeats, rename or
  delete that key.
- One race remains: an operator who creates exactly that key between the
  marker write and the create gets it adopted as the replacement.

## Permissions

Permissions are plain transit ACL policies, attached to the client's cert role.
With `<mount>` the transit mount, the operations need:

| Operation               | Method   | Path                                     | Capability                                  |
| :---------------------- | :------- | :--------------------------------------- | :------------------------------------------ |
| Create                  | `GET`    | `<mount>/keys/<name>`                    | `read` (a template with stored attributes)  |
|                         | `POST`   | `<mount>/keys/<name>`                    | `update`                                    |
|                         | `GET`    | `<mount>/keys/<name>/metadata`           | `read` (a template with stored attributes)  |
|                         | `POST`   | `<mount>/keys/<name>/metadata`           | `update` (a template with stored attributes) |
|                         | `DELETE` | `<mount>/keys/<name>/soft-delete`        | `delete` (that write failed, no Name given) |
| Register                | `GET`    | `<mount>/wrapping_key`                   | `read`                                      |
|                         | `POST`   | `<mount>/keys/<name>/import`             | `update`                                    |
|                         | `GET`    | `<mount>/keys/<name>/metadata`           | `read` (a template with stored attributes)  |
|                         | `POST`   | `<mount>/keys/<name>/metadata`           | `update` (a template with stored attributes) |
|                         | `DELETE` | `<mount>/keys/<name>/soft-delete`        | `delete` (only when that write fails)       |

|                         | `GET`    | `<mount>/keys/<name>/metadata`           | `read` (initial read and before the metadata write) |
|                         | `GET`    | `<mount>/keys/<predecessor>`             | `read` (a `<name>.<n>` without a record)    |
|                         | `GET`    | `<mount>/keys/<predecessor>/metadata`    | `read` (same optional predecessor check)     |
|                         | `POST`   | `<mount>/keys/<name>/metadata`           | `update`                                    |

|                         | `LIST`   | `<mount>/keys`                           | `list` (otherwise), then `read` on each key |

|                         | `GET`    | `<mount>/keys/<name>/metadata`           | `read` (initial read and before the metadata write) |
|                         | `DELETE` | `<mount>/keys/<name>/soft-delete`        | `delete` (a key not soft-deleted yet)       |
|                         | `POST`   | `<mount>/keys/<name>/metadata`           | `update` (not for a Destroyed object)       |
| Encrypt                 | `POST`   | `<mount>/encrypt/<name>`                 | `update`                                    |
| Decrypt                 | `POST`   | `<mount>/decrypt/<name>`                 | `update`                                    |

| SignatureVerify         | `POST`   | `<mount>/verify/<name>`                  | `update`                                    |
| Query, DiscoverVersions | –        | answered by the listener                 | –                                           |

Get exports through `encryption-key` for AES and ChaCha20 keys, `hmac-key` for
HMAC keys, and `signing-key` for RSA and ECDSA keys.

When writing a policy, keep in mind:

- **Revoke and Destroy need the soft-delete path and the metadata.** Both
  read `<mount>/keys/<name>`, read and update its metadata, and delete
  `<mount>/keys/<name>/soft-delete`. Neither sends a `DELETE` to
  `<mount>/keys/<name>`, so `delete` on that path is no longer needed. Denying
  `delete` on `<mount>/keys/<name>/soft-delete` denies Revoke and Destroy: each
  fails at the soft-delete, which Destroy skips only for a key soft-deleted
  already. Revoke has written the record by then, so the object reports
  Compromised or Deactivated while transit still serves the key. Activate
  reads the metadata, and updates it for a Pre-Active object. Policies with
  exact grants for these operations need the new paths.

- **Grant `update`, not `create`, on `<mount>/encrypt/*`.** Transit's encrypt
  endpoint creates a missing key for a caller that holds `create`, so that
  grant would let Encrypt create keys outside Create.

- **The export grant is the only guard on key material.** Create and Register
  make keys with `exportable=true` so Get can return their material, and
  transit cannot undo that. Leave out `read` on `<mount>/export/*` for clients
  that only need cryptographic operations.

- **ReKey needs a glob.** ReKey works on the key, its replacement
  `<name>.<n>`, and the Name's anchor, including their `/metadata` and
  `/soft-delete` paths. Grant them with a glob such as `<mount>/keys/app-*`;
  an exact grant on `<mount>/keys/<name>` is not enough. Without `delete` on
  `/soft-delete`, ReKey succeeds but old generations stay readable.

- **Locate by Name needs the same glob once the Name was rekeyed.** It reads
  the anchor `<name>`, then the current generation `<name>.<n>`. A role with
  only an exact grant on `<mount>/keys/<name>` gets an empty result, not an
  error, because a denied Locate read counts as no match.

- **Destroy keeps a rekeyed Name.** The first generation of a rekeyed Name
  holds the record that resolves the Name. Destroy keeps the key and its
  record, so any generation can be destroyed and Locate by Name still finds
  the current one.

- **Restoring an older backup rolls a rekeyed Name back.** A transit restore
  under the key's own name brings back the key's metadata record as it was
  when the backup was taken, including the anchor's `current` and the
  Replaced and Replacement Object Links. If the Name was rekeyed after the
  backup, Locate then returns a superseded generation and the next ReKey
  fails. After such a restore, set the anchor's `current` back to the newest
  generation. KMIP stores each entry as a JSON array of strings, written as one
  string value, so the request is:

  ```json
  PATCH <mount>/keys/<anchor>/metadata
  {"custom_metadata": {"kmip/current": "[\"<anchor>.<n>\"]"}}
  ```

  `PATCH` needs the `patch` capability. A `kmip/` value in any other form makes
  that key invisible to KMIP Locate and fails its other KMIP operations. A
  restore under a new
  name writes no metadata. A same-name restore advances the metadata version
  above both the backup and existing record, including a cleared record.
  Deleting and creating a key again resets its version to 0.

- **Locate without an exact Name or UID reads every key.** It lists the mount
  and reads each key. Name, State, and stored-attribute filters also read
  metadata. Denied key or metadata reads skip that candidate. Each read is
  audited and counts against quotas, so on large mounts prefer locating by
  name.

- **The policy applies beyond KMIP.** The same certificate can usually also log
  in to the cert auth mount through an HTTP listener and receive a token with
  the same policies, so grant only what the KMIP operations need. A glob such as
  `<mount>/keys/app-*` also matches paths the listener never calls, such as
  `<mount>/keys/app-1/config` and `<mount>/keys/app-1/rotate`.

When a request is denied, the KMIP error names the path and the capability the
policy is missing.

## Limits and reload

- `max_connections` `(integer: 1024)` limits accepted connections, including TLS
  handshakes. Connections above the limit close without a KMIP reply.
- `idle_timeout` `(duration: "10m")` closes a connection if it sends no complete
  request within this time. Partial frames do not extend the deadline. Closing
  a connection revokes its live service token.
- `max_request_size` `(integer: 1048576)` limits the complete TTLV frame in bytes,
  including its header and padding. This limit is separate from the HTTP JSON
  request size. A larger limit permits larger allocations per connection.

Negative values are invalid. Zero selects the default. `max_connections` and
`idle_timeout` are valid only on KMIP listeners. SIGHUP reloads these three
limits by listener address; existing connections keep their idle and frame
limits. The connection count limit applies to the next accepted connection.
TLS certificate reload also refreshes the listener certificate expiry metric.

## Audit records

Each KMIP batch item produces one request record and one response record through
OpenBao's audit devices. This includes discovery, login failures, malformed
frames, header refusals, and items cancelled after a batch error. Malformed
frames with no decoded operation use `Unknown`. Normal transit audit records
remain enabled.

The records use the standard audit format:

- `type` is `request` or `response`. Both records use the same `request.id`,
  generated by the server for this item.
- `request.operation` is `read` for Get, GetAttributes, GetAttributeList, Locate,
  Query, and DiscoverVersions; it is `update` for other operations.
- `request.path` is `<mount>/kmip/<Operation>`, or `kmip/<Operation>` before
  login identifies the mount. `mount_point` is `<mount>/` when known and
  `mount_type` is `transit`. `request.namespace` identifies the auth mount's namespace.
- The standard connection fields contain `remote_address`, `remote_port`, and
  `client_certificate_serial_number`.
- `auth` contains the accessor, entity ID, policies, token policies, identity
  policies, and metadata after login. The first request has an empty `auth`
  object because login occurs during the operation. The session token is never
  put in the KMIP record.
- `request.data` contains `kmip_operation`, `client_certificate_subject`,
  `unique_identifier` or `unique_identifiers` when present, and `transit_mount`
  when known. The response contains the same metadata plus `outcome`,
  `result_reason`, `result_message`, and `transit_request_ids`. The IDs link to
  all HTTP requests caused by the operation, including denials and forwarding.
- A failure sets the top-level `error`. Audit result messages use fixed text;
  client replies can have more specific diagnostics authored by the listener.

These metadata keys are excluded from HMAC, so paths, subjects, identifiers,
and results are visible to audit consumers. Other standard fields retain the
audit device's HMAC rules. KMIP records contain no bodies, Names, key bytes,
plaintext, ciphertext, signatures, wrapped keys, or tokens.

This abbreviated example pair shows a Get after login. Standard fields such as
`time`, `namespace`, and the HMAC-protected identity fields are omitted here:

```json
{"type":"request","request":{"id":"f59fa12e-7062-42ad-9787-b539a14de564","operation":"read","path":"transit/kmip/Get","mount_point":"transit/","mount_type":"transit","data":{"kmip_operation":"Get","client_certificate_subject":"CN=app.example.com","unique_identifier":"app-key","transit_mount":"transit"}}}
{"type":"response","request":{"id":"f59fa12e-7062-42ad-9787-b539a14de564","operation":"read","path":"transit/kmip/Get","mount_point":"transit/","mount_type":"transit","data":{"kmip_operation":"Get","client_certificate_subject":"CN=app.example.com","unique_identifier":"app-key","transit_mount":"transit"}},"response":{"data":{"kmip_operation":"Get","client_certificate_subject":"CN=app.example.com","unique_identifier":"app-key","transit_mount":"transit","outcome":"success","result_reason":"","result_message":"","transit_request_ids":["5cbda157-5ce1-47d1-9713-bbbe14c7f39d"]}}}
```

If request auditing fails, no item executes. If response auditing fails, the
client receives General Failure and the operation may already have completed.
Inspect transit records before retrying a write. A sealed store refuses every
operation with a sealed message. Unsealing restores service on the same listener.

## Metrics and alerts

The listener emits these metrics through OpenBao telemetry. All have `listener`
(the listening address) and the standard `cluster` label:

| Metric | Kind | Additional labels |
| :-- | :-- | :-- |
| `kmip.connections_open` | Gauge | None |
| `kmip.connections_accepted` | Counter | None |
| `kmip.connections_refused` | Counter | `reason`: `limit` or `handshake` |
| `kmip.operations` | Counter | `operation`, `outcome`: `success` or the KMIP Result Reason |
| `kmip.operation_duration` | Summary, milliseconds | `operation` |
| `kmip.errors` | Counter | `reason`: KMIP Result Reason, or `sealed` |
| `kmip.server_certificate_expiry_seconds` | Gauge | None |
| `kmip.client_certificate_expiry_seconds` | Gauge | `subject` |

Operation and reason labels use known names or a fixed fallback. Identifiers
and key names never become metric labels. Certificate subjects have unbounded
cardinality: use a controlled set of subjects. With several active connections
for one subject, the gauge uses their earliest certificate expiry. Certificate
gauges refresh every 30 seconds and on connection or certificate changes.

Closed subjects stop being emitted. Their last values can remain visible until
`prometheus_retention_time` expires (default `24h`); set a suitable retention
window and allow for stale samples in alerts. Prometheus replaces dots with
underscores and normally prefixes metric names with `vault_`. The examples
below assume `disable_hostname = true` and the default telemetry prefix:

```yaml
groups:
  - name: kmip
    rules:
      - alert: KMIPListenerCertificateExpiry
        expr: vault_kmip_server_certificate_expiry_seconds < 7 * 24 * 3600
        for: 5m
      - alert: OpenBaoSealed
        expr: vault_core_unsealed == 0
        for: 1m
      - alert: OpenBaoMetricsAbsent
        expr: absent(vault_core_unsealed)
        for: 5m
      - alert: KMIPSealedRefusals
        expr: sum by (listener) (increase(vault_kmip_errors{reason="sealed"}[5m])) > 0
      - alert: KMIPClientCertificateExpiry
        expr: vault_kmip_client_certificate_expiry_seconds > 0 and vault_kmip_client_certificate_expiry_seconds < 7 * 24 * 3600
        for: 5m
```

`OpenBaoSealed` uses the core `vault.core.unsealed` gauge, so it detects a
sealed node with no KMIP traffic. `KMIPSealedRefusals` fires only when clients
are refused. If a sealed node does not serve metrics to your scraper,
`OpenBaoMetricsAbsent` fires instead.
Scrape `/v1/sys/metrics` with a monitoring credential held outside this store,
so a sealed store cannot prevent access to the credential. Configure metrics
access on the HTTP listener for the node states that monitoring must cover.

## `kmip` listener examples

### Serving KMIP from the root namespace

This example serves KMIP on all IPv4 interfaces. Clients log in through
`auth/cert`, and clients whose role names no transit mount use `transit`.

```hcl
listener "kmip" {
  address               = "0.0.0.0:5696"
  tls_cert_file         = "/etc/openbao/kmip.crt"
  tls_key_file          = "/etc/openbao/kmip.key"
  tls_client_ca_file    = "/etc/openbao/kmip-clients-ca.pem"
  auth_mount            = "auth/cert"
  default_transit_mount = "transit"
}
```

The following policy, `kmip-app`, lets a client use every operation on keys
named `app-*` in the `transit` mount:

```hcl
# Create, Get, GetAttributes, GetAttributeList, Activate, Locate with a name,
# Revoke, and Destroy use transit/keys/<name>; Register uses
# transit/keys/<name>/import; Create and Register with stored template
# attributes, the attribute operations, Activate, ReKey, Revoke, and Destroy
# use transit/keys/<name>/metadata; Revoke, Destroy, and ReKey's retention
# use transit/keys/<name>/soft-delete. The glob covers all of them, and the
# replacements ReKey names <name>.2, <name>.3, and so on.
path "transit/keys/app-*" {
  capabilities = ["read", "update", "delete"]
}

# Locate without a name.
path "transit/keys" {
  capabilities = ["list"]
}

# Register.
path "transit/wrapping_key" {
  capabilities = ["read"]
}

# Get. Leave this out to keep key material inside OpenBao.
path "transit/export/+/app-*" {
  capabilities = ["read"]
}

# Encrypt, Decrypt, Sign, and SignatureVerify. Grant update, not create.
path "transit/encrypt/app-*" {
  capabilities = ["update"]
}

path "transit/decrypt/app-*" {
  capabilities = ["update"]
}

path "transit/sign/app-*" {
  capabilities = ["update"]
}

path "transit/verify/app-*" {
  capabilities = ["update"]
}
```

Enable the mounts, write the policy, and create a cert role for the client.
`kmip_key_prefix=app-` makes keys created without a name fall under the
policy's `app-*` paths.

```shell-session
$ bao secrets enable transit
$ bao auth enable cert
$ bao policy write kmip-app kmip-app.hcl
$ bao write auth/cert/certs/app \
    certificate=@kmip-clients-ca.pem \
    allowed_common_names=app.example.com \
    token_policies=kmip-app \
    token_ttl=1h \
    kmip_transit_mount=transit \
    kmip_key_prefix=app-
```

### Serving KMIP from a namespace

To serve a namespace, include it in `auth_mount`. The transit mounts named by
the cert roles and by `default_transit_mount` are in the same namespace.

```hcl
listener "kmip" {
  address            = "0.0.0.0:5696"
  tls_cert_file      = "/etc/openbao/kmip.crt"
  tls_key_file       = "/etc/openbao/kmip.key"
  tls_client_ca_file = "/etc/openbao/kmip-clients-ca.pem"
  auth_mount         = "ns1/auth/cert"
}
```

Create the mounts, policy, and role in `ns1`. Policy paths are relative to the
namespace, so the `kmip-app` policy above works unchanged.

```shell-session
$ bao namespace create ns1
$ bao secrets enable -namespace=ns1 transit
$ bao auth enable -namespace=ns1 cert
$ bao policy write -namespace=ns1 kmip-app kmip-app.hcl
$ bao write -namespace=ns1 auth/cert/certs/app \
    certificate=@kmip-clients-ca.pem \
    allowed_common_names=app.example.com \
    token_policies=kmip-app \
    kmip_transit_mount=transit \
    kmip_key_prefix=app-
```

A listener serves a single namespace. To serve several, configure one `kmip`
listener per namespace, each on its own address.
