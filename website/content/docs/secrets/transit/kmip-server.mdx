# Transit KMIP Server

The transit secrets engine can act as an embedded **KMIP (Key Management
Interoperability Protocol) server**. External KMIP clients such as databases,
storage arrays, and backup software can connect via mTLS to a TLS listener
spawned by the transit backend and use the standard KMIP protocol to create,
manage, and use transit-managed cryptographic keys.

## Overview

When the KMIP server is enabled on a transit mount, OpenBao:

- Starts a dedicated TLS listener (default port `5696`) that accepts KMIP
  connections from clients.
- Authenticates each client by its TLS certificate Subject Distinguished Name
  (DN) and maps it to a configured KMIP role.
- Routes KMIP operations (Create, Get, Encrypt, Decrypt, Sign, etc.) to the
  corresponding transit backend operations.
- Enforces per-role operation and key-name restrictions.

Keys created via KMIP are regular transit keys and can be managed through the
standard transit API as well.

## Supported KMIP Protocol Versions

KMIP versions **1.2**, **1.3**, and **1.4** are supported.

## Supported KMIP Operations

| KMIP Operation  | Mapped Transit Operation     |
|-----------------|------------------------------|
| Create          | keys/\<name\> (create)       |
| Register        | keys/\<name\>/import         |
| Get             | export/\<type\>/\<name\>     |
| GetAttributes   | keys/\<name\> (read)         |
| Locate          | keys (list)                  |
| Activate        | no-op (keys auto-activate)   |
| Revoke          | keys/\<name\> (soft-delete)  |
| Destroy         | keys/\<name\> (delete)       |
| Encrypt         | encrypt/\<name\>             |
| Decrypt         | decrypt/\<name\>             |
| Sign            | sign/\<name\>                |
| Verify          | verify/\<name\>              |
| Query           | returns server capabilities  |

## Supported Key Types

The following KMIP cryptographic algorithms map to transit key types:

| KMIP Algorithm       | Bit Length | Transit Key Type     |
|----------------------|------------|----------------------|
| AES                  | 128        | `aes128-gcm96`       |
| AES                  | 256        | `aes256-gcm96`       |
| RSA                  | 2048       | `rsa-2048`           |
| RSA                  | 3072       | `rsa-3072`           |
| RSA                  | 4096       | `rsa-4096`           |
| ECDSA / EC           | 256        | `ecdsa-p256`         |
| ECDSA / EC           | 384        | `ecdsa-p384`         |
| ECDSA / EC           | 521        | `ecdsa-p521`         |
| ChaCha20-Poly1305    | 256        | `chacha20-poly1305`  |
| ChaCha20-Poly1305    | 256        | `xchacha20-poly1305` |

## Authentication Model

The KMIP server uses mutual TLS (mTLS) for authentication. Each connecting
client must present a valid certificate signed by the configured CA. The
client's certificate Subject DN is matched against the configured KMIP roles.

### Roles

A **KMIP role** maps a client certificate Subject DN to:

- A list of **allowed KMIP operations** (e.g., `Create`, `Encrypt`, `Decrypt`).
- An optional list of **allowed key names**. If empty, the role has access to
  all keys on the transit mount.

If no role matches the client certificate's Subject DN, the connection is
rejected with `OperationNotAllowed`.

## Setup

### 1. Enable the transit engine

```shell-session
$ bao secrets enable transit
```

### 2. Configure the KMIP server

You need a TLS certificate/key pair for the KMIP server and optionally a CA
certificate to verify client certificates.

```shell-session
$ bao write transit/config/kmip \
    enabled=true \
    listen_addr="0.0.0.0:5696" \
    server_cert_pem=@/path/to/server-cert.pem \
    server_key_pem=@/path/to/server-key.pem \
    tls_ca_cert_pem=@/path/to/ca-cert.pem \
    require_client_cert=true
```

### 3. Create KMIP roles

Create a role that maps a client certificate Subject DN to allowed operations:

```shell-session
$ bao write transit/kmip/roles/my-db-client \
    cert_subject_dn="CN=mydb,OU=ops,O=example,C=US" \
    allowed_operations="Create,Locate,Encrypt,Decrypt,GetAttributes,Destroy" \
    allowed_key_names="db-key-1,db-key-2"
```

To allow access to all keys, omit `allowed_key_names` or leave it empty.

### 4. Connect with a KMIP client

Configure your KMIP client to connect to `<openbao-host>:5696` using the CA
certificate for server validation and the client certificate/key matching the
Subject DN configured in the role.

## Configuration Reference

### `transit/config/kmip`

| Parameter            | Type    | Default           | Description                                                     |
|----------------------|---------|-------------------|-----------------------------------------------------------------|
| `enabled`            | bool    | `false`           | Whether the KMIP server is enabled.                             |
| `listen_addr`        | string  | `0.0.0.0:5696`   | TCP address the KMIP server listens on (`host:port`).           |
| `server_cert_pem`    | string  | (required)        | PEM-encoded TLS certificate for the KMIP server.                |
| `server_key_pem`     | string  | (required)        | PEM-encoded private key for the KMIP server certificate.        |
| `tls_ca_cert_pem`    | string  | —                 | PEM-encoded CA certificate used to verify client certificates.  |
| `require_client_cert`| bool    | `true`            | Whether to require and verify client TLS certificates.          |

`server_key_pem` is write-only and never returned in read responses.

### `transit/kmip/roles/<name>`

| Parameter            | Type            | Description                                                                    |
|----------------------|-----------------|--------------------------------------------------------------------------------|
| `cert_subject_dn`    | string          | Subject DN of the client certificate that maps to this role.                   |
| `allowed_operations` | list of strings | KMIP operations the role may perform. See valid values below. Empty means all operations are allowed. |
| `allowed_key_names`  | list of strings | Transit key names this role may access. Empty means all keys are allowed.      |

Valid `allowed_operations` values: `Create`, `Get`, `GetAttributes`, `Locate`, `Destroy`, `Activate`, `Revoke`, `Register`, `Encrypt`, `Decrypt`, `Sign`, `SignatureVerify`, `Query`.

Note: the KMIP Verify operation string is `SignatureVerify` (matching the KMIP spec), **not** `Verify`. Using `Verify` will result in the operation being rejected at runtime.

### Listing roles

```shell-session
$ bao list transit/kmip/roles
```

## Lifecycle

The KMIP server starts automatically when the transit backend initializes if
`enabled=true`. It stops when the transit mount is unmounted or the backend
is cleaned up. Updating the `config/kmip` path restarts the server with the
new configuration automatically.

## Security Considerations

- Always use `require_client_cert=true` in production to enforce mTLS
  authentication.
- Use a dedicated CA to issue KMIP client certificates, separate from your
  general PKI.
- Scope roles to the minimum required operations and key names following the
  principle of least privilege.
- The KMIP listener port (`5696` by default) should be firewalled and accessible
  only to trusted KMIP clients.
- `server_key_pem` is stored encrypted in OpenBao storage and is never returned
  via the API.
